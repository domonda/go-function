# Architecture

go-function lets you write a plain Go function once and call it from a CLI, an HTTP endpoint, an HTML form, or your own code, without writing glue code per function and per transport. This page explains how the pieces fit together and why they are shaped the way they are.

## The problem

A function like this is easy to call from Go:

```go
func Convert(ctx context.Context, degrees float64, to string) (float64, error)
```

Exposing it anywhere else takes a lot of code. An HTTP handler has to read `degrees` and `to` from the query or body, parse `degrees` as a float, return 400 when that fails, call the function, encode the result, and map the function's error to a status. A CLI command repeats the same parsing for positional arguments, prints help text listing the argument names and types, and prints the result. A form needs an input per argument with a matching type.

Every function times every transport is another copy of that code, and the copies drift: the CLI accepts `1e3` but the HTTP handler doesn't, the form calls a field `deg` while the JSON API calls it `degrees`.

## The approach

go-function splits the work into one wrapper per function and one adapter per transport:

```
            func Convert(ctx context.Context, degrees float64, to string) (float64, error)
                                           │
                     function.ReflectWrapper(Convert, "ctx", "degrees", "to")
                     or generated by gen-func-wrappers from function.WrapperTODO(Convert)
                                           │
                                           ▼
  ┌──────────────────────────────── function.Wrapper ─────────────────────────────────┐
  │ Description           Name, String, ArgNames, ArgTypes, ArgDescriptions, ...      │
  │ Call                  []any                 ◄── htmlform.Handler (parses itself)  │
  │ CallWithStrings       positional strings    ◄── cli dispatchers                   │
  │ CallWithNamedStrings  map[string]string     ◄── httpfun.Handler                   │
  │ CallWithJSON          JSON object           ◄── your code, message queues, ...    │
  └───────────────────────────────────────────────────────────────────────────────────┘
                   │ strings go through function.ScanString
                   ▼
           one conversion engine for every string-based transport
```

A **wrapper** knows one function: its argument names and types, and how to call it from four kinds of input. An **adapter** knows one transport: how to get input from an HTTP request or a command line, and how to write results and errors back. Adapters never know about specific functions, and wrappers never know about HTTP or terminals.

Each adapter depends on the smallest interface it needs:

- `httpfun.Handler` takes a `CallWithNamedStringsWrapper`. HTTP query parameters, form fields, and the fields of a JSON body all arrive as name-value pairs.
- The `cli` dispatchers take a full `Wrapper`. They use `CallWithStrings` for positional arguments and the `Description` for help text.
- `htmlform.Handler` of the separate module [go-htmlform](https://github.com/domonda/go-htmlform) takes a full `Wrapper`. It uses the `Description` to render one input per argument, then parses the submitted values itself and calls `Call` with typed values. It can't use a string convention, because uploaded files must reach the function as `fs.File` values, never as strings that could name a file on the server (see [Security model](explanation-security-model.md)), and validators run on the parsed values before the call.

### One conversion engine

Every string-based input goes through [`function.ScanString`](reference-string-conversion.md): CLI arguments, URL query parameters, form fields, and even the fields of a JSON request body read by `httpfun.RequestBodyJSONFieldsAsArgs`, which passes JSON strings as their text and other values as their JSON text, like `42` or `[1,2]`. Arguments of type `any` get the string itself. Teaching `ScanString` a type once, by implementing `encoding.TextUnmarshaler` or registering a scanner, makes it work in all of those places at the same time.

`CallWithJSON` is the exception: it uses `json.Unmarshal`, because JSON carries its own types and Go types already define how they decode from JSON.

### Results and errors

The wrapper separates a last `error` result from the other results and returns them as `([]any, error)`. Adapters handle the two sides with their own output type:

- `cli` passes them to `function.ResultsHandler`s, like `function.Println`.
- `httpfun` and `htmlform` pass them to an `httpfun.ResultsWriter`, like `httpfun.RespondJSON`, and errors on to error handlers.

Argument parse errors carry the wrapper that failed (`ErrParseArgString.Func`). That lets `httpfun.Handler` tell two situations apart that look identical otherwise: the request sent `degrees=hot` (the client's fault, 400 Bad Request), or the function internally called another wrapper with bad data (the server's fault, 500). The wrapper is recognized if it's the one passed to `Handler`, the value it points to, or embedded in a decorating struct. Behind a function adapter like `function.CallWithNamedStringsWrapperFunc` it can't be, so invalid arguments are answered with 500 there. See [HTTP status codes](reference-http-status-codes.md).

### Panics

The `Call*` methods don't recover panics, because the wrapper can't know what a caller wants to do with them. Adapters decide: `httpfun.Handler` recovers them if `httpfun.CatchHandlerPanics` is true (the default) and answers 500, `htmlform.Handler` always does, and `cli` lets them crash the program like any other panic in `main`. Both HTTP handlers let a panic with `http.ErrAbortHandler` through, because a handler uses it to make `net/http` abort the response.

## Why ReflectWrapper needs argument names

```go
function.MustReflectWrapper(Convert, "ctx", "degrees", "to")
```

Go's `reflect` package exposes a function's argument types, but not their names. Parameter names aren't part of a function's type: `func(degrees float64)` and `func(d float64)` are the same type, and the compiled binary doesn't keep the names. Named conventions like `CallWithNamedStrings`, `CallWithJSON`, query parameters, and form fields need them, so `ReflectWrapper` takes them as strings.

The cost: nothing ties those strings to the source. `ReflectWrapper` checks that the count matches, but renaming a parameter in the source doesn't rename the HTTP query parameter.

The code generator reads the names from the source instead, together with argument descriptions from the doc comment, which then show up in CLI help and as form labels.

## Reflection vs. generated wrappers

Both kinds implement the same `Wrapper` interface with the same behavior, so you can switch between them without changing callers.

| | `ReflectWrapper` | Generated by `gen-func-wrappers` |
|---|---|---|
| Setup | none | add `WrapperTODO`, run `go generate` |
| Argument names | strings you pass | from the source |
| Argument descriptions | none | from `argName: description` lines in the doc comment |
| Calling the function | `reflect.Value.Call` with every argument boxed in a `reflect.Value` | a direct Go call |
| Source changes | wrapper adapts to new types at runtime, the passed names may be stale | changed argument types or counts stop the generated code from compiling, changed result types and renamed arguments and descriptions keep the old ones in `String`, `ResultTypes`, `ArgNames`, and `ArgDescriptions` until you regenerate, `-validate` reports all of them in CI |
| Works for | any function value, including closures and functions chosen at runtime | functions declared in source, including functions of other packages like `strings.ToUpper` |

String parsing costs the same for both, because both call `ScanString` for every argument that isn't of type `any`. The difference is the call itself and the type checks of `Call`.

Use `ReflectWrapper` to get started, for closures, and for code that picks functions at runtime. Use generated wrappers for functions that are part of your API, where names, descriptions, and compile-time checks pay off. [How to switch to generated wrappers](howto-generated-wrappers.md) walks through the change.

## Why the generator rewrites WrapperTODO in place

```go
var convert = function.WrapperTODO(Convert)
```

`gen-func-wrappers` replaces this declaration with a type and methods in the same file, instead of writing a separate generated file. The wrapper stays where you declared it, with the name you chose, and there is no second file whose name or package has to match.

Until you run the generator, `WrapperTODO` panics with `function.WrapperTODO: run gen-func-wrappers` at program start, because package-level variables are initialized before `main`. A forgotten generation step fails immediately, not later on the first request.

The cost is that generated code sits in your source file, and regenerating it changes that file. `gen-func-wrappers -validate` checks in CI that the generated code matches the current function signatures and doc comments.

## Global configuration

Conversion and HTTP behavior are configured with package-level variables: `function.StringScanners`, `TimeFormats`, `TimeLocation`, `MaxSliceLiteralElements`, and in `httpfun` the variables `HandleError`, `PrettyPrint`, `CatchHandlerPanics`, and the request size limits.

This keeps the API small: a wrapper or handler needs no options to behave consistently with every other one in the process. The trade-off is that the settings apply to the whole process and must be set once at startup, before handlers run. They are not safe to change while requests are in flight.

`TypeStringScanners` softens this for scanners: a value never changes after creation, and its `With` methods return modified copies. Configuring scanners is one assignment to `StringScanners`, and it can't change a `TypeStringScanners` value that other code holds.

`htmlform.Handler` has per-handler settings (validators, input types, size limit, cross-origin protection) because forms differ more from each other than API endpoints do.

## Earlier designs

The [CHANGELOG](../CHANGELOG.md) records several designs that v1.0.0 replaced:

- **Multiple query values joined with `;`.** `RequestQueryArgs` used to pass `?x=1&x=2` as `1;2`, which a `[]int` argument couldn't parse and a `[]string` argument got as one element. It now passes `["1","2"]`, a slice literal that `ScanString` already understands.
- **Single string parsed as a slice in `CallWithStrings`.** A lone string for a variadic argument used to be parsed as a slice literal, so a value that happened to look like `[...]` changed meaning. Every string from the variadic position on is now one element, like in a Go call. `CallWithNamedStrings` still parses `"[1,2]"`, because a single named value has no other way to carry several elements.
- **`Must` dispatch methods in `cli`.** `MustDispatch` and its siblings panicked for user input like an unknown command. They were removed: input from users is an error to report, not a programming bug.
- **Argument values in error messages.** `ErrParseArgString` used to add the argument value to its message, on top of the scanner error that already quoted it, and `ErrParseArgsJSON` held a copy of the JSON input. Both were dropped, because values can be large or private. The scanner error still quotes the value once, and HTTP responses name only the argument.
